학습 루프 Phase D — 품질 평가기 지연 · GPU 자원 경합 측정 계획

작성 2026-11-05, ai07 세션. 도구 fastapi/scripts/quality_gate_contention_probe.py (테스트 tests/test_lq_phase_d_contention_probe.py).
이 문서의 수치 중 "실측"은 이 세션에서 실제로 돌린 것이고, "미측정"은 운영 GPU 를 점유해야 해서 실행하지 않은 것이다.


1. 왜 따로 재야 하는가

  운영 AI 는 RTX 5070 Ti 16GB 한 장에서 Ollama 로 돈다. 학습메이트 생성(qwen3:14b), 화면 판독(qwen3-vl, :11435), 그리고 judge 를 켜면
  품질 평가(qwen3:14b)가 모두 같은 GPU 를 나눠 쓴다. EC2 게이트는 평가 1회 상한 8초, 동시 평가 2(bulkhead) = ai07 세마포어 2, 대기 2초다.
  judge OFF(현재 기본) 평가는 CPU 정규식·토큰 비교뿐이라 GPU 를 쓰지 않지만, 같은 프로세스의 이벤트 루프와 CPU 를 생성 경로와 나눠 쓴다.
  따라서 두 가지를 구분해 잰다.
    가. judge OFF 결정적 평가기의 CPU 지연과 이벤트 루프 점유(지금 바로 잴 수 있음, GPU 무관)
    나. judge ON 일 때 같은 GPU 를 쓰는 생성과 평가가 서로 얼마나 느려지는가(운영 GPU 점유 필요)


2. 이번에 실측한 것: cpu 단계 (GPU·Ollama·네트워크 미사용, 합성 입력)

  명령: cd fastapi && python -m scripts.quality_gate_contention_probe --out <파일>
  조건: judge OFF, 세마포어 2, 대기 2초(운영 route 와 같은 규칙), 요청마다 originalRequest 를 달리해 평가 캐시 적중 제외.
  입력은 실제 Spring 이 보내는 모양이다: 로드맵은 EC2 분할기와 바이트 동일한 2만 자 세그먼트(헤더+주차 묶음 5개),
  PDF QA 는 계약 최대치(출력 5.7만 자 + 근거 32개 × 8천 자), 퀴즈 10문항 JSON, 비전 답변 + 관측 1개.

  결과(ms, 평가 1회 단독 p50 / 동시 8 에서 p95, 동시 8 대기 초과 비율):
    로드맵 세그먼트(379~18,107자)     7.9 / 53.8,  대기 초과 0/32
    PDF QA 계약 최대치                 1,286 / 2,614(동시 2부터 대기 포함),  대기 초과 동시 4 에서 8/16, 동시 8 에서 24/32
    퀴즈 10문항                        2.3 / 2.3,   대기 초과 0/32
    비전 답변                          0.15 / 0.15, 대기 초과 0/32
  이벤트 루프 지연(다른 요청이 느끼는 멈춤) p95: 로드맵 10.6, PDF QA 최대치 10.7(최대 36), 퀴즈 13.3, 비전 1.0.

  해석:
    로드맵 84일 전체(세그먼트 5개)는 평가기 쪽 합계 약 40ms 다. 분할 평가가 평가기 지연 문제를 만들지 않는다.
    계약 최대치 근거·출력을 동시에 받으면 평가 1회가 1.3초 CPU 를 쓴다. 동시 4 이상이면 세마포어 2 와 대기 2초 때문에 절반 이상이 429 가 된다.
    실제 PDF QA 출력은 수천 자 수준이라 흔하지 않지만, 최악 입력에서는 Spring 사용자별 한도(분당 30)보다 평가기 동시성이 먼저 막힌다.
    이것은 합성 CPU 측정이다. 운영에서는 같은 CPU 를 생성·임베딩·스트리밍과 나눠 쓰므로 더 느릴 수 있다.

  원자료: 이 세션 scratchpad 의 probe_cpu2.json(커밋하지 않음). 같은 명령으로 재현 가능하다.


3. 실행하지 않은 것: gpu 단계 (미측정)

  운영 GPU 를 실제로 점유하는 측정이라 이번에는 돌리지 않았다. 사전 점검(--dry-run)만 실행했고 결과는 시작 가능 상태였다
  (VRAM 85MiB 사용, 사용률 0%, 34°C, 적재 모델 없음). dry-run 은 nvidia-smi 와 Ollama /api/ps 읽기만 한다.

  시나리오(도구에 구현됨):
    G0 기준선: judge 평가만 순차 10회(생성 없음)
    G1 생성 1스트림(num_predict 256) + judge 평가 10회 동시
    G2 생성 2스트림 + judge 평가 10회(동시 평가 2)
    G3 G2 + 화면 판독 모델(qwen3-vl, :11435) 적재 상태
    G4 judge OFF 결정적 평가 20회 + 생성 2스트림(CPU 경합만)
  기록 항목: 평가 지연 p50/p95/p99/최대, 생성 토큰 속도(TPS) 변화, VRAM 최고치, GPU 온도 최고치, 오류·timeout 수.

  안전장치(코드로 강제):
    시작 조건: --allow-gpu 플래그와 환경변수 AI_CONTENTION_PROBE_ALLOW=1 둘 다(없으면 GPU_PHASE_NOT_AUTHORIZED 로 종료),
      GPU 사용률 20% 이하, 온도 55°C 이하, VRAM 여유 3GiB 이상, 대상 모델 외 다른 모델 미적재.
    중단 조건: 온도 60°C 이상(QLoRA 온도 가드와 같은 기준), VRAM 15GiB 이상, 오류 3회, 총 10분, 총 120호출.
    합성 입력만 쓴다(사용자 데이터 없음). 운영 모델 태그·설정·keep_alive 정책은 바꾸지 않는다(호출마다 keep_alive 60s).

  실행 절차(운영 승인 후):
    1) 운영 트래픽이 적은 시간대를 정하고 사용자에게 알린다. 학습메이트·화면 AI 가 그 동안 느려질 수 있다.
    2) judge 설정을 측정용 프로세스 env 에만 준다(AI_QUALITY_JUDGE=qwen3:14b 등). 운영 서비스 .env 는 건드리지 않는다.
    3) --phase gpu --dry-run 으로 사전 점검 → 통과하면 AI_CONTENTION_PROBE_ALLOW=1 ... --phase gpu --allow-gpu 실행.
    4) 결과 JSON 을 인계서에 붙이고, 아래 판정 기준으로 judge 운영 여부와 동시성 값을 정한다.

  판정 기준(제안, EC2 와 합의 필요):
    judge ON 평가 p95 ≤ 6초(Spring timeout 8초의 75%) 이고 생성 TPS 저하 ≤ 30% 일 때만 judge 를 학습메이트에 켠다.
    G3 에서 VRAM 최고치가 15GiB 를 넘으면 judge 와 화면 판독을 동시에 운영하지 않는다(모델 교대 적재 지연이 생긴다).
    judge ON 이면 Spring bulkhead·ai07 세마포어를 1~2 로 다시 정하고, Spring 사용자별 평가 한도(분당 30)를 평가기 처리량에 맞춰 낮춘다.
